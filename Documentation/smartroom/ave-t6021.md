Target: omacom/linux-aurora only. Not for AsahiLinux.

Branch: `smartroom/ave-t6021`

The driver is imported from aurora-silicon `integration/aurora` commit
`145922a30cc66893ba60a4cafd16d2197876e5f6`
(`drivers/media/platform/apple/ave`). omacom/linux-aurora does not carry it.
This branch adds the t6021 match and the M2 Max device-tree nodes.

## Why t8112's boot parameters

t6021 (M2 Max) is the same generation as t8112 (M2). Both use coprocessor
family `ave_coproc_6070` and firmware 6070.11.1, with TEXT `0xd0000` and
DATA `0x128000`. The t6021 variant copies t8112's boot identity: device 18,
type 15, boot arg `0x10000`, timebase multiplier 1, extra0 `0x4000`, and
DATA restored before the first start.

t6000 (M1 Pro) is the previous generation. It uses the same segment sizes
and the same register block, but device 14 / type 11 and a timebase
programmed in microseconds (`timebase_multiplier` 1000000). t6041, t8140,
t8142, and t6050 are the M4 / A18 / M5 coprocessor (`ave_coproc_v40`) with
larger firmware images. ave1 is a second instance of the t6021 block, not
a different variant.

`text_crc` is 0. `ave_fw_probe()` then accepts either known 6070 image
(t8112 `25bfd039` or t6000 `460c7a7c`); both select `ave_layout_6070_11_1`,
which has `encode_ready`. The segment-size check still rejects the M4/M5
images. Any other TEXT CRC fails probe with
`unsupported firmware (text CRC %08x)`. That CRC is the value to record.

## Device tree

Register layout is the aurora-silicon `t6021-peripherals` ave0/ave1
description (codec, mailbox, coproc, power-control, fabric, four DARTs
each). Nodes are enabled on t6021. t6020 includes `t6021.dtsi` and deletes
`pmgr_south`, which owns `ps_venc1_*`, so t6020 deletes ave1 and its DARTs.

No `memory-region` is written here. The Aurora Stage 2 loader attaches two
`apple,asc-mem` / `no-map` reservations and records
`/chosen/aurora,ave-text-crc32` and `aurora,ave-data-crc32`. Inventing
physical addresses would point the driver at the wrong RAM. Without that
handoff, probe stops with `no preloaded firmware` and does not register
`/dev/video`.

## Suggested PR text

Subject: media: apple: add the t6021 AVE encoder

Import the V4L2 mem2mem AVE encoder from aurora-silicon and match
`apple,t6021-ave` on the M2 Max. The block is the M2 6070.11.1 encoder, so
the boot parameters are t8112's. Either qualified 6070 TEXT CRC selects the
6070 command layout; an unknown CRC is printed and refused. ave0 and ave1
are described from the t6021 register map. Firmware stays a bootloader
handoff (`memory-region` plus the two `/chosen` CRCs). The M2 Pro drops
ave1 with `pmgr_south`.

## Test plan (Claude, on the Studio)

After installing `linux-aurora` `7.2.11.aurora14-1.sr1` and rebooting:

```
uname -r
# expect 7.2.11-14-1.sr1-ARCH

for d in /sys/class/video4linux/video*; do
  echo "$(basename "$d") $(cat "$d/name")"
done
dmesg | grep -i -E 'ave|apple-ave'
```

A bound encoder is a `/dev/videoN` named `Apple AVE video encoder`.
Two instances can show up. Then:

```
ffmpeg -f lavfi -i testsrc=size=1280x720:rate=30 -frames:v 30 \
  -pix_fmt nv12 -c:v h264_v4l2m2m -b:v 4M /tmp/ave-smoke.h264
ls -l /tmp/ave-smoke.h264
```

These dmesg lines are a completed test, not a crash to paper over. Copy
them into the report:

- `no preloaded firmware` — Stage 2 did not attach two `memory-region`s
- `unsupported firmware (text CRC --------)` — record that CRC
- `unexpected firmware segment sizes`
- `firmware must start its DART window`
- `firmware text differs from loader CRC` or `firmware data is not in its boot state`
- `encoding refused: firmware TEXT`

Width must be a multiple of 16. NV12 in, H.264 Annex B out.
